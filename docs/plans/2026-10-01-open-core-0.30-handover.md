## 2. What 0.30 contains

### 2a. Validation uplift (the headline)

The founder's goal (2026-09-30): "Get it to 134/223 for 0.30". **134 is a ceiling, not a quota.** A
row is promoted only when an independent oracle agrees within a tolerance written down before the
comparison. The honest expected result is about 110 to 120. Tell the founder this plainly; never
tune a tolerance to reach a number.

Done already, on `feat/validation-uplift` in `~/Code/kshana-wt-validation`:

- Wave 0 (`f394b5ba`): the promotion rule in `docs/VALIDATION.md`. Every VALIDATED row declares its
  oracle kind in `validated_oracle_basis()` in `src/verification.rs`, enforced by
  `tests/verification_rows_declare_an_oracle_basis.rs` and mutation-tested.
- Round 1 (`7737bedc`): +10 rows (M008, M021, M045, M056, M059, M080, M085, M090, M106, M120), each
  with its tolerance fixed in advance and a second reviewer.
- A real defect fixed: the DE440 lunar-orientation interpolation was off by up to about 340 m; now
  about 3 m (`src/lunar_orientation.rs`).
- **20 oracles disagreed.** They are recorded as findings, not failures: M002, M010, M011, M018,
  M019, M034, M035, M038, M047, M057, M061, M073, M076, M083, M088, M091, M093, M109, M124, M127.
- 2 were downgraded because the test does not discriminate: M041, M111.
- 19 are blocked on decisions, tools or data (section 3 and the plan's "Known blockers").
- One promotion record per row in `~/Code/kshana-site-next/research/validation-0.30/records/`
  (`Mnnn.md`, plus `B2/B3/B6/B7-PREREGISTRATION.md`).
- Batch worktrees still on disk: `~/Code/kshana-wt-val-b1` … `-b10` (branches `feat/val-b1` …
  `feat/val-b10`). The integrator already merged them into `feat/validation-uplift`. Check with
  `git branch --merged feat/validation-uplift` before removing any of them.
- At round 1, 4 tests failed in the full suite; all 4 were fixed. **The full re-run was still
  pending.** Run it before anything else on that branch.

The oracle toolchain is durable at `~/Code/kshana-oracles/`. Read `README.md` there first:
`source env.sh` before any generator, `setup.sh` rebuilds it from empty, and `data/MANIFEST.md`
lists each dataset with its licence and SHA-256 (417 datasets, about 1.1 GB).

**Step 7: local gates, then push, then tag.** The order is fixed.
1. Receipt gate on a clean tree at the exact release commit, in the worktree:
   ```
   TEST_THREADS=8 scripts/gate.sh
   ```

2. Local runners:
   ```
   ~/Code/kshana-site-next/scratch/actlocal/rerun.sh <sha>
   ```
   (`QUICK=1` skips the multi-hour jobs; `ONLY="..."` runs named entries). If `pages-site-check` is red, check `scratch/actlocal/check_site.py`; it now understands `<base href>`.
3. **Push only from the main checkout `~/Code/kshana`**, on branch `main`. The pre-push contract `.ci-native` is untracked and exists only there; pushing from a worktree fails with "no local gate in this repository".
   ```
   git merge --ff-only <sha>
   cp <worktree>/.gate-receipt.json .
   git push origin main
   ```
4. Annotated tag:
   ```
   git tag -a v0.30.0 <sha> -F <message file>
   git push origin v0.30.0
   ```
   The tag push starts `release.yml`.
5. Deploy the site from the tag (pages.yml runs only on dispatch):
   ```
   gh workflow run pages.yml --repo ashfordeOU/kshana -f tag=v0.30.0
   ```
6. Live check:
   ```
   node ~/Code/kshana-site-next/features/check_nav.mjs https://kshana.dev --jobs 4
   ```
   Expect 0 BAD on phone and desktop. Then fetch `/`, `/studio/`, `/studio/advanced/`, `/docs/`, `/robots.txt`, `/sitemap.xml` and `/llms.txt`.
7. Watch the release run to completion (watchers stop after 2 hours; restart if needed). Then check channel parity, purge the badges, and report.
