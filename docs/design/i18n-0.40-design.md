# Translations for kshana.dev, the docs, the Studio and the engine: design v2 (0.40, workstream J)

Languages (16; English is the source and the fallback): nl, pl, pt, fi, sv, da, nb, cs, uk, ru, de, fr, es, et, ja, zh-Hans. Plus the pseudo-locale `en-XA` for tests.
Status: design for review (v2, after the owner's "better systems" request). Nothing is built yet. Branch: kshana-pro `site/i18n-0.40`.

## 0. The decisions in one paragraph

One message system everywhere: **Project Fluent** (`.ftl`). One catalogue per language, shared by the site, the docs, the Studio and the engine (W55, fluent-rs). The same `.ftl` files are read in the browser and at build time by one JavaScript implementation (`@fluent/bundle`, vendored, hash-pinned, plus the browser and Node `Intl`), so a page built at deploy time and the same page re-rendered in the browser say the same thing. Keys are stable ids for application text (`studio-run-button`) and content hashes for document text (`seg-<sha12>`), which makes the translation memory exact. The language follows the user (browser languages on a first visit, an explicit choice remembered), the `/<lang>/` URL stays canonical and shareable, numbers and dates come from `Intl`, and an accented, 35 % longer pseudo-locale in CI catches every hard-coded string and every overflow.

## 1. Where the files live and how they flow (one repository, no copies)

Home of the catalogues: the **kshana repository, `i18n/`** (the engine reads it too; the port copies it into `web/i18n/` for the site and the Studio):

```
i18n/
  en/            the source (English). Written by hand (ui, engine, glossary) or generated by `extract` (pages)
    ui.ftl         site chrome, notices, switcher, Studio interface text      ids: site-*, studio-*, notice-*
    engine.ftl     text the engine writes for people (summaries, axis titles, verdict lines)   ids: engine-*   (W55)
    glossary.ftl   terms: -tier-validated, -tier-modelled, -tier-partner, -verdict-not-met, -kind-*, -cmd-*, -unit-*, -advisory
    pages/<page>.ftl   the text of one built page, one message per segment, id seg-<sha12 of the English segment>
  <lang>/        the same file names; a translator copies an en file and translates the values, keeping every id and every placeable
  numfmt.json    generated once from Node's ICU: the number separators per locale (for build time)
```

Flow: (1) I write `en/ui.ftl`, `en/glossary.ftl`, and the tools; `extract` writes `en/pages/*.ftl` from the built English pages (the port commits them). (2) W57 and W58 translate `i18n/<lang>/**` and run `node tools/i18n.mjs check <lang>` locally. (3) W55 writes `en/engine.ftl` and the Rust side (fluent-rs, `include_str!` of the same files, a `--lang` flag and an API argument); the plural and placeable lint below runs on the engine ids too. (4) kshana CI runs `check` and the coverage report; `pages.yml` runs `apply` to expand the language trees (section 3). `docs/design/i18n-0.40-design.md` stays in kshana-pro; the formats are also described in `i18n/README.md` (to write).

## 2. Fluent usage rules

- English `.ftl` is the source. No string concatenation in code: a sentence is one message with placeables (`{ $n }`), terms (`{ -tier-validated }`) and selectors. Plurals and grammatical case and gender use Fluent selectors and term attributes, which matter for pl, cs, uk, ru, fi, et:
  `studio-ledger-rows = { $n -> [one] { $n } ledger row *[other] { $n } ledger rows }`; a Finnish or Polish translator writes the categories their language needs. `check` reads the required categories from `Intl.PluralRules(<lang>).resolvedOptions().pluralCategories` (cs, pl, ru, uk: one, few, many, other; fi, et, de, nl, sv, da, nb, es, pt, fr: one, other (pt, fr, es also `many`); ja, zh-Hans: other) and fails on a select that lacks one.
- A translated message must have exactly the English message's placeables and variables; it may add terms. Term attributes carry case (`-kind-clock = clock .gen = …`).
- Markup inside a message is limited to numbered tags that stand for the English element: `<a1>…</a1>`, `<b>`, `<em>`, `<c1/>` (a code span, kept verbatim). `apply` maps them back to the English element and its attributes; a translation cannot add an element, a script or an attribute.
- Document text (the site pages and the 199 docs pages): the English page is cut into segments (block text and the text attributes: title, alt, aria-label, meta description). Every number, code span, URL and ledger or verdict word is a placeable, so the translator cannot change it. The message id is `seg-` plus the first 12 hex digits of the SHA-256 of the English segment skeleton.

## 3. Translation memory, fallback, coverage

- The id is the translation memory. An unchanged English segment keeps its id, so its translations are reused (also on another page, and after an edit elsewhere on the page). A changed segment gets a new id: it is **missing** in every language until retranslated, and the old id becomes an orphan (reported, harmless, removable).
- A missing or stale segment is shown in English. A page with any English fallback shows, at the top of its content and in its language, "N parts of this page have changed since they were translated and are shown in English." (UI message `notice-fallback`, with the count as a plural variable); a page with none shows only the machine-translation notice. The build never uses a translation whose id does not match the current English segment.
- `node tools/i18n.mjs status [--json]` prints, per language and page, **translated / stale / missing** segment counts, plus the orphan ids, the pages not started, and the plural and placeable errors. W57 and W58 work from it.
- URLs and hreflang as in v1: English at the root, `/<lang>/…` for the site and docs; a `/<lang>/…` page exists for every English page (a page with nothing translated is the English page with the notice, `rel=canonical` to English, no hreflang alternate for itself); hreflang plus `x-default` on translated pages; `sitemap.xml` is an index of `/<lang>/sitemap.xml`, each listing only pages with at least 80 % of their segments translated.
- The 16 language trees are generated at deploy time (`apply`, a pure function of the English tree plus `i18n/`), not committed. Only the catalogues are committed (text).

## 4. The language follows the user

1. **First visit** (nothing stored): the page's inline script reads `navigator.languages` and matches against the 17 locales (exact tag, then the language: `de-AT` to de, `no`/`nn` to nb, `zh-CN`/`zh-SG`/`zh-Hans-*` to zh-Hans, `zh-TW`/`zh-HK` to English), else English. On an English page it redirects once to `/<lang>/<same path>` (`location.replace`, no history entry) and says so in a dismissible line ("Showing Deutsch. Switch to English"). A static host cannot read Accept-Language; `navigator.languages` is that header's client-side twin. Crawlers and visitors without script get English.
2. **An explicit choice** in the switcher is stored (`localStorage` key `kshana-lang`, every read and write in try/catch, per viewer) and wins over detection. English is a choice too.
3. **Carries across** the site and the Studio (same origin, same key); the Studio also reads `?lang=` and the `/<lang>/studio/…` stub (a 2 KB page that sets the language and goes to `/studio/…`). A `/<lang>/` URL opened directly shows that language for that page and does not overwrite the stored choice, so a shared link is stable.
4. **The Studio changes language without reloading**: `l10n.setLang(lang)` loads the bundle, updates every `data-l10n` element and re-runs the page's render hooks; a run in progress and the current result are untouched.

## 5. Locale-aware formatting (Intl)

- Numbers (`NUMBER($n, maximumFractionDigits: 1)`: 1,408 / 1 408 / 1.408), dates, and relative time use `Intl.NumberFormat`, `DateTimeFormat`, `RelativeTimeFormat` with the page's locale, in the browser and at build time (Node, full ICU). Units: SI symbols stay as they are (`m`, `ns`, `dB-Hz`, `%` follows the locale's spacing rule); unit names in running text come from the glossary.
- Never localised: code, file names, command lines, JSON keys and codes, scenario and kind ids, URLs.
- **The integrity check compares values, not strings**: it parses every number in the final translated page with that locale's separators (`numfmt.json`) and compares the multiset of numeric values (and each unit symbol) with the English page's. It also compares code spans, hrefs and the verdict and tier tokens (as ids, through the glossary), and requires the advisory message (`-advisory`) and the machine-translation notice on the page. Any difference fails the build.

## 6. Glossary

`en/glossary.ftl` defines the terms; `<lang>/glossary.ftl` fixes the rendering of each: kept (a term whose translation is itself: VALIDATED, MODELLED, PARTNER, NOT MET may be kept or given one fixed translation), or one exact translation, with case attributes where the language needs them. Kinds, scenario files and commands are generated from the engine register and are always kept. The build fails when a segment contains an English glossary term and the translation does not use the language's rendering of it. `-advisory` is the exact advisory sentence per language. The tier and verdict words in pages and in the Studio badge render through these terms; the machine attributes (class names, data attributes, CSV, JSON) stay English.

## 7. The Studio and the engine output

- `lib/l10n.mjs` (replaces the planned i18n.mjs): `t(id, vars)`, `setLang(lang)`, `onChange(fn)`, English fallback per id, formatting through Intl, the vendored `@fluent/bundle`. Static HTML text carries `data-l10n="id"` with the English as the fallback content. The strings built in `app.js` and `advanced.js` (about 190 KB each) move to ids page by page; the coverage figure is reported.
- **Engine output localised wherever it is for people**: the engine (W55) accepts `lang` (CLI `--lang`, API argument) and writes its human-facing text (summaries, report text, chart axis titles and legends, verdict lines) from `engine.ftl`; machine fields stay English. The Studio passes the current language to every run. A recorded result was made in English: it is shown in English with a small label ("recorded in English"). The evidence badge, the verdict words and the Studio's own charts are localised in the Studio through the same catalogue.
- A hard-coded string is a bug: `check` scans the Studio and site JavaScript for text literals reaching the DOM outside `t()` (a lint), and the pseudo-locale test (next) finds the rest.

## 8. Pseudo-locale `en-XA`, and CI

`tools/i18n.mjs pseudo` generates `en-XA` from the English catalogue: accented letters, about 35 % longer, wrapped in brackets, placeables and markup untouched. CI runs the site and Studio tests and Playwright screenshots (1440 and 390 px) in `en-XA`, and in German and Finnish for length. It fails on (a) any visible text node on a page without the bracket markers that is not marked as engine output or code (a hard-coded string), (b) horizontal overflow, (c) a missing id (fallback to English in a translated build is reported, not fatal; in `en-XA` it is fatal).

## 9. RTL-ready layout

None of the 16 is right-to-left, but the layout is made ready: `<html lang dir>` from the locale data; the site and Studio CSS use logical properties (`margin-inline`, `padding-inline`, `inset-inline`, `text-align: start`, `border-inline`, `float: inline-start`); a lint (`tools/i18n.mjs csslint`) lists the physical `left/right` properties that remain (an allow-list for charts and absolute geometry). The conversion is done file by file with before and after screenshots; an `en-XA` variant with `dir=rtl` is a test.

## 10. Size and fonts (as measured, v1)

Measured on the 106 MB 0.39.0 build: docs HTML 35.8 MB (25.3 MB of it inlined images: 578 uses of 201 files = 15.1 MB; the README page alone 13.8 MB); a copy of the docs text is about 10.5 MB. Plan: every inlined image becomes one shared file `assets/img/<sha12>.*` (English falls to about 96 MB); a language then adds about 13.5 MB; 16 languages about 312 MB plus the CJK subsets (under 1 MB). Hard cap 500 MB in check.py rule 12; the Pages limit is 1 GB. Added by this design: the vendored `@fluent/bundle` (about 35 KB) and the catalogues in `web/i18n/` (text, about 3 to 5 MB per language, served only to the pages and the Studio that use them).
Fonts: Cyrillic is covered by the site's local Geist, Geist Mono and Unbounded files; CJK (ja, zh-Hans) is a Noto Sans JP or SC subset generated from the characters the translations use (fontTools, woff2, one `unicode-range` face per language, 150 to 400 KB each, the OFL sources fetched once and hash-checked, not committed).

## 11. Suggested order of translation (unchanged)

1. `ui.ftl` and `glossary.ftl` (small, decides the vocabulary), then the 7 site pages. 2. Docs index, overview, concepts, glossary, tutorials. 3. The other prose docs. 4. The pages that are mostly engine-authored English (verification matrix, capability and scenario reference, the 99 kind pages, the changelog): translate their chrome and prose; leave the tables English, labelled, unless the owner wants them translated word for word (decision needed).
