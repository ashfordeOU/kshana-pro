# Translations for kshana.dev, the docs and the Studio: design (0.40, workstream J)

Languages (16, English stays the reference): nl, pl, pt, fi, sv, da, nb, cs, uk, ru, de, fr, es, et, ja, zh-Hans.
Status: design for review. Nothing is built yet. Branch: kshana-pro `site/i18n-0.40`.

## 1. What is measured today (the 0.39.0 build, 231 pages, 106 MB)

| part | size | note |
|---|---|---|
| docs pages (199 html) | 35.8 MB | of which 25.3 MB are inlined `data:` images (578 uses, 201 distinct files = 15.1 MB); `docs/overview.html` (the README) alone is 13.8 MB, 13.8 of it images |
| docs text without the images | about 10.5 MB | this is what a language adds |
| site pages (7 html, root) | 2.7 MB | |
| shared data (search.json, land.json, series.json, sitemap, llms) | about 7 MB | search.json (0.37 MB) is per language |
| Studio (wasm 15.5, recorded runs 20.4 gz + 12.1 json, scripts, images) | about 57 MB | one copy, shared by every language |

The size is not the sixteen copies of the images alone; a copy of the docs text is 10.5 MB. So: a language costs about 13.5 MB if the images are shared files, and about 38 MB if they stay inlined.

## 2. Size plan (hard budget: 500 MB published; the Pages limit is 1 GB)

- Images: every inlined image becomes one shared file `assets/img/<sha256-first-12>.<svg|png|jpg>`, referenced by an absolute path from every page in every language. English alone drops from 106 MB to about 96 MB (25.3 MB inlined becomes 15.1 MB of files).
- Estimate with 16 languages: 96 MB + 16 x 13.5 MB = about 312 MB (plus CJK font subsets, section 8, under 2 MB). check.py rule 12 gets a hard cap of 500 MB and fails the build above it.
- Not committed in the built folder: the 16 language trees are generated at deploy time from English plus the translation files by a deterministic, offline step (same idea as port_site.py), so the repositories do not grow by about 216 MB per rebuild. Only the translation files (about 3 to 5 MB per language, text) are committed.

## 3. URLs, switcher, search engines

- English stays at the root. A language is a prefix: `/de/`, `/de/capabilities.html`, `/de/docs/rust.html`. Relative links between pages work unchanged inside a language tree; assets (css, js, images, data, Studio) are rewritten to absolute root paths.
- Studio: one copy, at `/studio/`. The language is a runtime setting (`?lang=de`, remembered in localStorage `kshana-lang`). `/<lang>/studio/...` are 2 KB stubs that set the language and redirect to `/studio/...?lang=<lang>`.
- Every page carries a language switcher (endonyms: Nederlands, Polski, Português, Suomi, Svenska, Dansk, Norsk bokmål, Čeština, Українська, Русский, Deutsch, Français, Español, Eesti, 日本語, 简体中文, English), linking to the same page in each language. The Studio has the same menu.
- `<html lang>` per page; `hreflang` alternates (all current translations plus `x-default` = English) on every page; a page that falls back to English at `/de/x.html` carries `rel=canonical` to the English page and no hreflang alternate for itself. `sitemap.xml` becomes a sitemap index with one `/<lang>/sitemap.xml` per language, listing only pages actually translated.

## 4. Translation storage: one file per page per language

Unit = a page key (path without `.html`, `/` as `__`: `docs/rust` -> `docs__rust`).

- `site-next/i18n/en/<page>.json`: the English segments, written by `i18n.py extract` from the built English page:
  `{ "page": "docs/rust", "skeleton_sha256": "<hash>", "segments": [ { "id": "s1", "tag": "p", "text": "The best site keeps the link up {{n1}} % of the time, {{c1}} …", "protect": { "n1": "75", "c1": "<code>…</code>" } }, … ] }`
- `site-next/i18n/<lang>/<page>.json`, written by the translator from that file:
  `{ "page": "docs/rust", "lang": "de", "source_sha256": "<the skeleton_sha256 it was translated from>", "segments": { "s1": "Die beste Site hält die Verbindung {{n1}} % der Zeit, {{c1}} …" }, "meta": { "translator": "machine", "date": "2026-11-01" } }`
- Protected tokens: every number, `<code>` span, `<pre>` block, URL, and ledger or verdict word (VALIDATED, MODELLED, PARTNER, MET, NOT MET, NEEDS INPUT, PASS, FAIL, DETECTED, LATE, MISSED) is replaced in the text by a placeholder `{{nK}}`, `{{cK}}`, `{{uK}}`, `{{wK}}`. The translator keeps the placeholders; the build puts the English value back. A translation therefore cannot change a number, a code span, a URL, a tier or a verdict, and a count that changes in English (388 rows to 390) does not make a translation stale.
- The hash covers only the skeleton (the translatable text with placeholders, in order). If the English skeleton changes, the page is stale.
- Never ship an out-of-date translation: at build, a missing translation or one whose `source_sha256` differs from the current skeleton falls back to the English page, served at the language URL with a translated notice (UI string `stale_notice`: "This page has changed since it was translated; showing English." in the language; or `missing_notice`). The page-level rule is deliberate: a half-translated page is worse than English.
- UI strings (switcher label, the two notices, the machine-translation line, nav labels): `site-next/i18n/ui/<lang>.json`, English in `ui/en.json`; the Studio catalogue reads the same files.

## 5. Glossary per language

- `site-next/i18n/glossary/_keep.json` is generated from the engine's feature register (scenario kinds, scenario files, command names, units, tier and verdict words): terms never translated. Tier and verdict words are already protected tokens; the glossary also covers them inside running text.
- `site-next/i18n/glossary/<lang>.json`: `{ "terms": { "holdover": "Holdover (Haltezeit)" , … }, "advisory": "<the advisory sentence, translated, exact>", "keep_extra": [ … ] }`: terms that must be translated exactly one way.
- The build fails if a segment contains an English glossary term and its translation lacks the required rendering, or lacks a "keep" term that its English had (verbatim, case-sensitive). W57 and W58 can write the glossaries now: the file format above, plus `advisory`.

## 6. Integrity check (check.py rule 26)

Per translated page: (a) the placeholder multiset of each translated segment equals the English one (so the numbers, code, URLs, tiers and verdicts are identical by construction); (b) a second independent pass compares the final built HTML: the sequence of numbers, code spans, hrefs and tier or verdict words equals the English page's; (c) the language's advisory sentence is present on the page; (d) the machine-translation line is present; (e) no `<script>` or attribute is added by a translation (segments are text only; HTML is escaped). Any failure fails the build.

## 7. The notice on every translated page

"Machine translation, not reviewed by a native speaker. English is the reference." (UI string `mt_notice`, in the page's language), with a link to the English page, at the top of the main content and in the footer.

## 8. Fonts

- Cyrillic (uk, ru): the site's local Geist, Geist Mono and Unbounded files already include the cyrillic subsets (they are in `fonts/files`), so no addition.
- CJK (ja, zh-Hans): a subset of Noto Sans JP or SC, generated at build from the characters the translations actually use (fontTools `pyftsubset`, woff2), one file per language, a `unicode-range` face loaded only on those pages. Estimate: 150 to 400 KB each, under 1 MB in total. The source fonts (OFL) are fetched once by a fetch script, hash-checked, not committed; only the subsets are.

## 9. The Studio

- `lib/i18n.mjs`: `t(key, vars)` with English fallback per key; catalogue `studio/i18n/<lang>.json` loaded on demand; static HTML text carries `data-i18n="key"` and its English as the fallback content; `?lang=` and localStorage choose the language.
- Engine output (result JSON, chart and table text, scenario titles and descriptions) stays English, and a small label "English, from the engine" appears where it shows.
- Scope: the interface chrome and the pages' fixed text in phase 1; the many strings built in app.js and advanced.js (about 190 KB each) move to catalogue keys page by page, with a coverage figure reported. A tool lists the keys used, and the keys missing per language.

## 10. Tools

- `i18n.py extract`: writes `i18n/en/*.json` from the built English pages.
- `i18n.py apply`: produces the language trees (a pure function of English pages plus i18n files); runs at deploy and in the site build.
- `i18n.py check`: the glossary and integrity checks.
- `i18n_status.py`: for each language, lists missing and stale pages (and, for a stale one, which segment ids changed), so W57 and W58 know what to do. Output: a table by language, and `--json`.

## 11. Order of translation for W57 and W58 (suggested)

1. The 7 site pages and the UI strings. 2. The docs index, overview, concepts, glossary, tutorials. 3. The other prose docs. 4. The reference pages that are mostly engine-authored English (verification matrix, capability reference, scenario reference, the 99 kind pages, changelog): these can ship with their page chrome and prose translated and the tables left English, labelled; "everything" needs the owner's decision on whether the tables are to be translated word for word.
