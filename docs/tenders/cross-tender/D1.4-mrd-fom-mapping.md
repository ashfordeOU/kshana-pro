## 1. Why this exists

The SoW asks for a Mission Requirements Document. The differentiator is not the
prose — any bidder can write prose — it is that **this MRD cannot drift from the
engine that is supposed to satisfy it**. The requirement table is encoded in code
(`mrd::mrd_table`), and three independent guards keep it honest:

1. every **measured** requirement is asserted to resolve to a real serialised FoM
   field on a concrete open-core struct (`FoMScores` / `CoverageReport` / `Dop` /
   `PositioningFom` / `SbasProtectionLevel`);
2. every measured requirement is asserted to resolve to a **live verification-matrix
   row**, and the row's `OracleKind` (ExternalDataset / ReferenceImpl /
   InternalConsistency) is carried straight onto the deliverable;
3. every **follow-on** requirement is asserted to claim *no* field and *no* oracle, so
   a real capability cannot be parked as a gap and a gap cannot quietly acquire a
   field without being re-classified;
4. no row may credit a **pass-through as a computation** — `PositioningFom.hpl_m`
   only carries a protection level the caller supplies, so a test forbids sourcing
   HPL/VPL from it.

These guards have already done their job once. Guard 3 previously froze the position
rows as partner/follow-on for as long as `positioning_performance()` returned `Err`.
When the open core implemented it, that assertion failed — which is the guard working,
not a broken test: the deliverable was marking a live, externally-validated capability
as "not available". The rows were re-classified against the engine and the guard was
re-pointed at the invariant that survives a capability landing.

A prime's systems engineer can therefore audit the requirement matrix against the
code, not against a claim. No GNSS-simulator competitor (GMV magicGNSS/RXAN, Qascom
SimSAFE) ships a requirement matrix whose every measured row is executably
cross-referenced to a validation oracle.


The first command regenerates the fenced block; the second fails if this document
has been hand-edited away from the code; the third fails if any measured row stops

or an oracle without being re-classified, or if a row credits a pass-through field as
a computation.

## 4. What this is NOT

- **Not an agreed requirement baseline.** It is a *skeleton* pending the real mission
  SRD; the numeric thresholds (timing budget, holdover floor, availability target)
  are deliberately left to the SRD, not asserted here.
- **Not an end-to-end position-accuracy claim.** CEP/SEP/2DRMS are computed, and the
  quantile kernel is externally validated (SciPy `rayleigh`/`maxwell`, plus a 6 M-draw
  NumPy Monte-Carlo median) — but they are a *transform of a covariance*, and that
  covariance comes from the MODELLED fusion EKF whose trajectory truth and sensor
  calibration are not externally validated. The number is real; the accuracy claim
  behind it is modelled.
- **Not integrity under GNSS denial.** Every protection level in the engine (SBAS
  DO-229E, ARAIM MHSS, lunar service-volume) is snapshot GNSS geometry. None bounds
  the coasting fused solution — MRD-INT-04, stated as an open gap.
- **Not flight-validated.** `MEASURED (VALIDATED)` refers strictly to an
  external-dataset oracle in the verification matrix (orbit/geometry), not to flight
  heritage. TRL ≤ 3.
- **Not a substitute for the prime's systems engineering.** It is the verification-
  traceable starting matrix Ashforde contributes as the performance-analysis WP.
