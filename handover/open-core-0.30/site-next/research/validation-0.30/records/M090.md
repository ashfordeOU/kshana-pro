## Pre-registration (written 2026-10-01T03:25Z, before any comparison was run)

Oracle kind: **Library**. Oracle: NAIF SPICE Toolkit via spiceypy 8.2.0 (MIT wrapper of CSPICE N0067,
https://github.com/AndrewAnnex/SpiceyPy), `pxform('MOON_PA_DE440', 'J2000', et)` evaluating the binary
PCK `moon_pa_de440_200625.bpc` directly, with the official NAIF frame kernel `moon_de440_250416.tf`
(not the hand-written frame text in scripts/gen_de440_moon_pa.py) and `naif0012.tls`.

Epochs: 2 000 epochs drawn uniformly (numpy default_rng seed 20261001) in the interior of the
embedded series' window (2024-01-01 TDB to 2025-12-31 TDB), so off the daily nodes almost surely;
Kshana's input is the same epoch as (et / 86400) / 36525, the convention the embedded series uses.

Tolerance (fixed now): the angle of the relative rotation R_kshana^T R_spice at most
**1.7e-5 rad** (30 m at the 1737.4 km mean radius) at every epoch. The module documents no tighter
interpolation bound: its doc comment states "<~0.06 deg" before renormalisation, and the guard test
bounds the one-day error below 600 m, both looser than 1.7e-5 rad, so the plan's 1.7e-5 rad applies.

Test: `tests/lunar_pa_orientation_spice_oracle.rs::interpolated_rotation_matches_direct_kernel_evaluation_off_node`;
fixture `tests/fixtures/lunar_pa_orientation_spice_oracle/`.

## Result

**Verdict: AGREES (after a defect fix the oracle exposed). Proposed: PROMOTE, kind Library.**

- First run (commit c3fabfb4, interpolator as it stood): worst rotation angle **1.960e-4 rad (340.5 m)**
  at et 817491986.4, RMS 1.387e-4 rad (240.9 m), above the 1.7e-5 rad bound. Diagnosis (no tolerance
  touched): at the daily nodes Kshana and SPICE agree to 1e-15 rad, so the series is right; the error is
  the interpolation. Element-wise linear interpolation plus Gram-Schmidt keeps the axis but not the
  angle of the 13.2 deg/day rotation; the angle error is zero at the interval midpoint and largest near
  the quarter points. The existing guard (`tests/lunar_pa_frame_realisation_guard.rs`) samples only
  midpoints, which is why the row text says "about 14 m".
- Defect fix (commit 15258d2c, `src/lunar_orientation.rs`, B1's module): geodesic interpolation
  `R0 Exp(f Log(R0^T R1))`. Node values unchanged.
- Second run, same fixture, same 1.7e-5 rad bound: worst **1.714e-6 rad (2.98 m)**, RMS 7.84e-7 rad (1.36 m).
- Findings for CHANGELOG: (1) the interpolator was in error by up to ~340 m off-node, now ~3 m;
  (2) the row's "about 14 m" figure and the guard's midpoint-only sampling understate it (the guard's
  bounds still hold after the fix: it compares fixture rows, not the engine). Downstream users
  (`lunar_llr_geometry`, `lunar_datum`, `lunar_faultobs`) get the corrected orientation; their tests
  and the lib unit tests pass.
