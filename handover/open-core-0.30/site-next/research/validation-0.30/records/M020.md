## Check (2026-10-01)

The existing test passes on `feat/val-b4` (`eo_payload_coverage_matches_skyfield_sgp4_and_wgs84_ellipsoid`).
Its tolerances predate this decision, so they are not post-hoc.

Verdict: **STAYS MODELLED as a whole-row relabel; needs an owner decision.** Reading the test against
the promotion rule finds three gaps the plan does not address:
1. **Claim coverage.** The row claims Earth angular radius, swath width, nadir GSD, maximum
   off-nadir access, circular period and ground-track spacing with a contiguous-coverage flag. The
   test compares only the limb (angular radius), maximum ground range and equatorial node spacing.
   Swath width, nadir GSD, maximum off-nadir access and period have no oracle.
2. **Oracle B is not an accepted independent oracle.** The limb angle and maximum ground range are
   compared with a WGS-84 ray-to-ellipsoid tangent computed by this repository's own numpy script
   (`tests/fixtures/eo_payload_coverage_geometry/generate_eo_payload_coverage_reference.py`), not by
   a third-party library. Under "What does not count" that is a script of our own (a different,
   more exact model, but still our implementation). Only oracle A (Skyfield 1.54 / SGP4 2.26 node
   spacing) is a Library oracle.
3. **The 1 % node-spacing bar does not hold across the row's domain.** The test validates it only for
   sun-synchronous orbits; at the ISS inclination (51.6 deg) Kshana under-estimates by 0.8 to 2.0 %
   (the J2 nodal regression it omits), which the test asserts only as a directional characterisation.

A promotable narrowing, for the owner to write before any relabel: "equatorial ground-track node
spacing of sun-synchronous orbits, within 1 % of Skyfield/SGP4", with the limb part either dropped
or re-checked against a third-party geodesic library. No new comparison was run in this batch.
