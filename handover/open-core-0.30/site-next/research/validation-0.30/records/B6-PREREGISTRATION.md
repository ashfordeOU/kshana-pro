## M059 (row 116) LAMBDA integer ambiguity resolution

- Oracle kind: Library. RTKLIB v2.4.2-p13 (git 71db0ffa, BSD-2-Clause,
  https://github.com/tomojitakasu/RTKLIB) `lambda(n, m=2, a, Q, F, s)` in `src/lambda.c`, compiled from
  C by a driver in the fixture directory (pattern of
  `tests/fixtures/time_transfer_error_budgeting/rtklib_driver.c`); only its numeric output is
  committed.
- Inputs: 300 problems generated by the driver from a fixed xorshift seed, n uniform in 2..=10.
  Covariance Q = (A A^T + 64 G G^T + I) / 256 with A (n x n) and G (n x 3) integer matrices with
  entries in [-9, 9]: every entry of Q is an exactly representable binary fraction, so both sides
  build bit-identical Q from the committed integers. The rank-3 term gives the elongated,
  geometry-dominated covariance typical of GNSS float ambiguities. Float vector a: uniform in
  [-50, 50] cycles, printed with 17 significant digits (exact round trip).
- Kshana under test: `kshana::lambda::resolve(Q, a)`; best squared norm = `residual`, second =
  `residual * ratio`.
- Tolerance: the fixed integer vector identical to RTKLIB's best candidate (F column 0) on all 300;
  the best and second-best squared norms each within 1e-9 relative of RTKLIB's s[0], s[1].
  Problems on which RTKLIB itself returns an error are counted and reported, not dropped silently.
- Test: `tests/lambda_rtklib_oracle.rs::ils_solution_matches_rtklib_lambda_on_300_covariances`.

## M127 (row 214) Joint GNSS pseudorange positioning with an inter-system bias

- Oracle kinds: Reference (ITRF2020 coordinate) + Library (RTKLIB rnx2rtkp v2.4.2-p13).
- Data: IGS station ABMF (97103M001), 2018-05-13, `ABMF00GLP_R_20181330000_01D_30S_MO.crx.gz`
  (BKG IGS archive, SHA-256 caacbbcc892123e382f126c2279f3e5902dd0e7fd302eded8902c21e416c71b1) and
  `BRDC00WRD_R_20181330000_01D_MN.rnx.gz` (BKG, SHA-256
  83374f15e83bca3b6b79e211bc2846ac5fdf8517467c50ec3f8d0f6033a336f3). Committed slice: epochs every
  300 s (288), GPS and Galileo only, the C1C observable only; the navigation file cut to GPS and
  Galileo records. Both Kshana and RTKLIB read the same committed slice.
- Truth: ITRF2020_GNSS.SSC ABMF solution 4 (valid from 2015:118), position at 2015.0 plus velocity
  times (epoch - 2015.0), epoch 2018-05-13 12:00. Antenna height 0 in the header, so no offset.
- Processing (same for both tools): single frequency (GPS L1 C/A C1C, Galileo E1 C1C), broadcast
  ephemeris, broadcast GPS Klobuchar ionosphere for both systems, Saastamoinen troposphere,
  10 deg elevation mask, one clock per system. Kshana: `pvt::assemble_epoch(dual_freq = false)`
  from the header a priori, each measurement handed to `leo_fusion::joint_pvt::solve` as
  pseudorange + sat clock - iono - tropo with sigma = 1/sin(el) m, systems GPS = 0 (reference) and
  Galileo = 1 (`SystemClock::Estimated`). RTKLIB: `rnx2rtkp` single mode with `out-solstat=1`; its
  `$CLK` record gives the GPS and Galileo receiver clocks (ns), ISB = Galileo - GPS.
- Tolerance: (a) at least 100 epochs solved and the 3-D error to the ITRF2020 coordinate <= 3 m at
  >= 95 % of solved epochs; (b) |median over common epochs of (ISB_Kshana - ISB_RTKLIB)| <= 1 ns.
  Reported, not graded: per-epoch 95th percentile of |ISB difference|, and the Kshana-RTKLIB
  position difference.
- Test: `tests/joint_pvt_itrf_rtklib_oracle.rs::multi_gnss_fix_matches_itrf2020_and_rtklib`.
