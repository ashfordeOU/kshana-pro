## Pre-registration (written 2026-10-01T03:30Z, before any comparison was run)

Oracle kind: **Library**. NaveGo v1.4 (git tag `v1.4`, commit 24d9488; its `navego_print_version`
still prints "release v1.3"), LGPL-3.0, run as a tool under GNU Octave 11.1.0, never linked or
copied into the crate. https://github.com/rodralez/NaveGo. The oracle is NaveGo's own
loosely coupled `ins_gnss.m` on its own real example dataset.

Dataset: NaveGo `examples/real-data/` (part of the NaveGo repository, LGPL-3.0): a 21-minute
land-vehicle drive, Ekinox IMU at 200 Hz, GNSS at 5 Hz, Ekinox reference trajectory at 1 Hz.
- `ekinox_imu.mat` SHA-256 b49466ed36c5b7de343e555ecd5822ce0cc47896911224d23ee6226f0ef526c5
- `ekinox_gnss.mat` SHA-256 13f8a2611ad6df24cb875593dac00702b31cb9125e69eb6ebd9b2c276a9bcd9c
- `ref.mat` SHA-256 a1e68052b4126c1af2f93deb44a4301ab54ef0693310d59e523a37a2732dbfab

"Same data" (fixed now). The full 200 Hz record (251 799 samples) is too large to commit, so both
filters run on one derived input: consecutive groups of 10 samples averaged (mean angular rate,
mean specific force, i.e. increment / interval) to 20 Hz, grouped so every GNSS epoch falls on a
group end, and rounded to float32. NaveGo and Kshana both read exactly these float32 values. NaveGo
keeps its example configuration otherwise unchanged (its ZUPT, its `gnss.eps`, its per-axis noise).
NaveGo on the original 200 Hz record is recorded for context only; it is not a criterion.

Kshana configuration (fixed now; Kshana's API takes isotropic scalars, so each per-axis NaveGo
value is mapped by root-mean-square or mean of squares, stated here once):
- `fusion::closed_loop::ClosedLoopInsGnss` around `fusion::gnss_ins_ekf::GnssInsEkf`.
- Initial state as NaveGo: attitude `imu.ini_align` (roll, pitch, yaw, ZYX), velocity `gnss.vel(1)`,
  position `gnss(1)`.
- IMU input: NaveGo's static calibration `imu.ab_sta`, `imu.gb_sta` subtracted from every sample
  (NaveGo subtracts the same values internally). Kshana's dynamic bias estimates start at zero.
- Initial sigmas: position RMS(`gnss.stdm`), velocity RMS(`gnss.stdv`), attitude
  RMS(`imu.ini_align_err`), accelerometer bias RMS(`imu.ab_dyn`), gyro bias RMS(`imu.gb_dyn`).
- Noise: `vrw_psd = mean(imu.vrw^2)`, `arw_psd = mean(imu.arw^2)`,
  `accel_bias_rw_psd = mean(imu.ab_psd^2)`, `gyro_bias_rw_psd = mean(imu.gb_psd^2)`,
  `accel_bias_tau = mean(imu.ab_corr)`, `gyro_bias_tau = mean(imu.gb_corr)`.
- A fix is fused at every GNSS epoch after the first, at the end of the coinciding 20 Hz step,
  with sigma_pos = RMS(`gnss.stdm`), sigma_vel = RMS(`gnss.stdv`). The GNSS antenna position and
  velocity are referred to the IMU with the lever arm `gnss.larm` by the same transform NaveGo
  applies inside its measurement (p_imu = p_ant - C_bn l; v_imu = v_ant - C_bn (w_ib x l) +
  W_in C_bn l), computed by the test harness from Kshana's current attitude. Kshana has no ZUPT.

Metric (fixed now, identical for both filters): each solution's latitude, longitude and height are
linearly interpolated at every reference epoch strictly inside the solution span; north error
= dlat (R_M + h_ref), east error = dlon (R_N + h_ref) cos(lat_ref) with WGS-84 radii, down error
= -dh. Horizontal RMS = sqrt(mean(N^2 + E^2)); vertical RMS = sqrt(mean(D^2)).

Pass criteria (tolerance fixed now; the 1.2x factor is the plan's). PROMOTE only if all four hold:
1. Kshana horizontal RMS <= 1.2 x NaveGo horizontal RMS.
2. Kshana vertical RMS <= 1.2 x NaveGo vertical RMS.
3. Innovations: over the GNSS epochs where NaveGo applied a position update (its non-ZUPT rows), the
   RMS of Kshana's 3-D position innovation (INS minus lever-arm-corrected GNSS, before the update)
   <= 1.2 x the RMS of NaveGo's 3-D position innovation (`nav.v` columns 4 to 6).
4. Not overconfident: the mean over all Kshana updates of |nu_p|^2 / (tr P_pp(prior) + 3 sigma_pos^2)
   <= 1.5.

Known weakness, stated before the run: GNSS is present at 5 Hz for the whole drive, so both
filters are held close to the GNSS track; criteria 1 and 2 test the filter mostly through how it
weights and lever-arm-corrects the fixes, not through coasting.

### Pre-run refinements (2026-10-01T05:3xZ local, before the Kshana comparison was run)

- NaveGo's `ins_gnss.m` calls the Octave control package's `obsv()` only for its diagnostic
  observable-state count (`ob`), which never feeds the solution; the package is not installed, so
  the generator adds a standard-definition stand-in (`octave_shims/obsv.m`).
- NaveGo stores its prior sigmas, not an innovation, in innovation row 1 (its initialisation
  call); criterion 3 therefore starts at GNSS row 2, as NaveGo's own update loop does.

Context (not a criterion): NaveGo on the original 200 Hz record scores 2.3309 m horizontal and

Reading of the result, for the row text: on this drive both filters sit about 2 m from the Ekinox
reference because both follow the 5 Hz GNSS fixes (stated weakness in the pre-registration); the
check shows Kshana's loosely coupled filter, configured only from NaveGo's published dataset
parameters, tracks a real IMU/GNSS record at least as well as an independent loosely coupled
implementation and is not overconfident. It does not test coasting through an outage.
